# SDD-first Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `spec-driven` Method Pack to Agora and make it the default lifecycle for new projects, while keeping Scrum and Kanban fully supported and unchanged.

**Architecture:** `spec-driven` is a Markdown Method Pack under `templates/methods/spec-driven/`, structured identically to `templates/methods/scrum/` and `templates/methods/kanban/` (same `agora/method/v1`, `agora/role/v1`, `agora/transition/v1`, `agora/gate/v1` schemas). No core engine code changes — `load_method_contract`, gates, transitions, and artifacts already handle any Method Pack generically. The only behavioral change to Python code is which method id three call sites default to when no `--default-method`/`method` is given.

**Tech Stack:** Python 3.11+, pytest, existing Agora Markdown-front-matter contract format (no new dependencies).

**Spec:** `docs/superpowers/specs/2026-08-16-sdd-first-design.md`

## Global Constraints

- No change to Scrum's or Kanban's `METHOD.md`, roles, transitions, or gates.
- No new core validation code — `spec-driven` must validate purely through the existing `load_method_contract` path used by scrum/kanban today.
- `--default-method scrum` and `--default-method kanban` must keep working exactly as today; only the *default value used when the flag is omitted* changes.
- Gate id `spec-clarified` must not collide with any existing gate id (confirmed clear via repo grep during design).
- `templates/methods` is copied wholesale into every new project by `AgoraWorkspace.initialize()` (`workspace.py:438`, `copy_template_tree(root / "methods", agora / "methods", ...)`) — adding the directory is sufficient for it to be installed; no separate registration step exists (`BUILTIN_METHODS` in `model.py` is presently unused by any runtime code path — update it for documentation accuracy only, not because anything reads it).

- [ ] **Step 4: Create `templates/methods/spec-driven/PROTOCOL.md`**

```markdown
# Spec-Driven protocol

The Spec Owner drafts the specification, resolves every open question, and holds final acceptance.
The Developer plans, implements, and verifies against the accepted specification. A spec cannot leave
drafting until its criteria are satisfied and a `spec` artifact is registered — clarification is a
gate, not a convention.

The same actor may hold both roles when project policy allows it, but the two responsibilities stay
distinguishable: clarifying scope is not the same action as implementing it.

Failed verification returns work to `implementing` for rework rather than inventing a new state; the
specification does not change mid-cycle without a new draft.
```

from pathlib import Path

import pytest

from agora.model import (
    AddActorInput,
    AddApprovalInput,
    AddArtifactInput,

    ConfigureInput,
    CreateSwarmInput,

from agora.workspace import AgoraWorkspace


def _workspace(tmp_path: Path, monkeypatch) -> AgoraWorkspace:
    monkeypatch.setenv("AGORA_HOME", str(tmp_path / "home"))
    workspace = AgoraWorkspace(cwd=tmp_path)
    workspace.configure(
        ConfigureInput(
            integration="generic",
            provider="configured-by-integration",
            model="configured-by-integration",
            default_method="spec-driven",
        )
    )
    workspace.initialize(InitInput())
    return workspace


def _form_swarm(workspace: AgoraWorkspace) -> None:
    workspace.add_actor(
        AddActorInput(
            id="owner", name="Owner", kind="human",
            capabilities=["specification", "acceptance"], scope="project",
        )
    )
    workspace.add_actor(
        AddActorInput(
            id="dev", name="Developer", kind="ai-agent",
            capabilities=["implementation"], scope="project",
        )
    )
    workspace.create_swarm(CreateSwarmInput(id="delivery", objective="Ship the increment"))
    workspace.assign_actor(
        AssignActorInput(swarm_id="delivery", role_id="spec-owner", actor_id="owner")
    )
    workspace.assign_actor(
        AssignActorInput(swarm_id="delivery", role_id="developer", actor_id="dev")
    )


def test_spec_driven_blocks_clarification_until_criteria_and_spec_artifact_exist(
    tmp_path: Path, monkeypatch
) -> None:
    workspace = _workspace(tmp_path, monkeypatch)
    _form_swarm(workspace)

    work = workspace.create_work(
        CreateWorkInput(
            swarm_id="delivery",
            id="increment",
            title="Add idempotency",
            actor_id="owner",
            description="Requests must be safe to retry.",
            acceptance_criteria=[("idempotent", "Retried requests do not duplicate effects")],
            required_artifacts=["spec"],
        )
    )
    assert work.state == "drafting"

    with pytest.raises(ValueError):
        workspace.transition_work(
            TransitionWorkInput(
                swarm_id="delivery", work_id="increment", actor_id="owner", target_state="clarified"
            )
        )

    workspace.satisfy_criterion(
        WorkActorInput(swarm_id="delivery", work_id="increment", actor_id="owner"),
        criterion_id="idempotent",
    )
    with pytest.raises(ValueError):
        workspace.transition_work(
            TransitionWorkInput(
                swarm_id="delivery", work_id="increment", actor_id="owner", target_state="clarified"
            )
        )

    workspace.add_artifact(
        AddArtifactInput(
            swarm_id="delivery", work_id="increment", actor_id="owner",
            kind="spec", uri="repo://docs/specs/increment.md",
        )
    )
    clarified = workspace.transition_work(
        TransitionWorkInput(
            swarm_id="delivery", work_id="increment", actor_id="owner", target_state="clarified"
        )
    )
    assert clarified.state == "clarified"

# Spec-driven delivery with humans and AI agents

This guide shows how Agora's bundled Spec-Driven Development Method Pack governs a mixed team. It
models role authority, transition policy, artifacts, evidence, and acceptance around a single
discipline: nothing gets planned until the specification is clarified.

## Scenario

A team must add idempotency to a payment API:

- A human or AI actor acts as Spec Owner: drafts the specification, resolves every open question, and
  holds final acceptance.
- A human or AI actor acts as Developer: plans, implements, and verifies against the clarified
  specification.
- The configured LLM environment executes AI actors, but Agora determines their allowed role actions.

Configure a Codex-backed environment while keeping concrete model selection in Codex:

```bash
agora configure \
  --integration codex \
  --provider openai \
  --model configured-by-codex \
  --default-method spec-driven

cd payment-service
agora init
```

`spec-driven` is already the default, so `--default-method` above is shown for clarity, not
necessity.

## Spec-driven contract

The installed pack is `.agora/methods/spec-driven`. Its roles are:

| Role | Required capabilities | Actor kinds | Primary authority |
| --- | --- | --- | --- |
| Spec Owner | `specification`, `acceptance` | human, AI agent, swarm | Create work, satisfy criteria, accept completion |
| Developer | `implementation` | human, AI agent, swarm | Plan, implement, verify, record artifacts and evidence |

The delivery path is:

```text
drafting -> clarified -> planned -> implementing -> verifying -> completed
```

The graph also permits `verifying -> implementing` for rework. `drafting -> clarified` carries the
`spec-clarified` gate: it fails unless every acceptance criterion on the work item is satisfied and a
`spec` artifact is registered. This is Agora's expression of Spec-Driven Development's "resolve
ambiguity before planning" discipline — enforced by the same gate mechanism every Method Pack uses,
not by a separate tool or a convention someone can skip under deadline pressure.

Agora checks actor kind, capabilities, assignment, allowed action, exact transition edge, and gate
policy for every mutation. The graph is supplied by the Method Pack rather than hard-coded into an LLM
prompt.

## Register the team

```bash
agora actor add --scope user \
  --id spec-owner --name "Human Spec Owner" --kind human \
  --capability specification --capability acceptance

agora actor add \
  --id developer --name "AI Developer" --kind ai-agent \
  --capability implementation

agora swarm create --id payment-api --objective "Deliver an idempotent payment endpoint"
agora swarm assign --swarm payment-api --role spec-owner --actor user:spec-owner
agora swarm assign --swarm payment-api --role developer --actor developer
```

## Draft and clarify

```bash
agora work create \
  --swarm payment-api --id idempotent-endpoint \
  --title "Add idempotency to the payment endpoint" \
  --description "Retried requests must not duplicate effects." \
  --by spec-owner \
  --criterion "idempotent:Retried requests do not duplicate effects" \
  --required-artifact spec --required-artifact test-report
```

Work starts in `drafting`. The transition to `clarified` fails until the criterion is satisfied and
the `spec` artifact exists:

```bash
agora work criterion-satisfy --swarm payment-api --work idempotent-endpoint \
  --criterion idempotent --by spec-owner

agora artifact add --swarm payment-api --work idempotent-endpoint \
  --kind spec --uri repo://docs/specs/idempotent-endpoint.md --by spec-owner

agora work transition --swarm payment-api --work idempotent-endpoint \
  --to clarified --by spec-owner
```

## Plan, implement, and verify

```bash
agora work transition --swarm payment-api --work idempotent-endpoint --to planned --by developer
agora work transition --swarm payment-api --work idempotent-endpoint --to implementing --by developer

agora artifact add --swarm payment-api --work idempotent-endpoint \
  --kind source-code --uri repo://src/payments.py --by developer

agora work transition --swarm payment-api --work idempotent-endpoint --to verifying --by developer

agora artifact add --swarm payment-api --work idempotent-endpoint \
  --kind test-report --uri ci://builds/1/tests --by developer
agora evidence add --swarm payment-api --work idempotent-endpoint \
  --type test-run --result success --artifact ci://builds/1/tests --by developer
```

If verification fails, return to implementation instead of inventing a new state:

```bash
agora work transition --swarm payment-api --work idempotent-endpoint --to implementing --by developer
```

## Accept and complete

```bash
agora approval add --swarm payment-api --work idempotent-endpoint \
  --role spec-owner --by spec-owner --note "Accepted for completion"

agora work transition --swarm payment-api --work idempotent-endpoint --to completed --by spec-owner
```

The final transition fails without satisfied criteria, every required artifact kind, successful
evidence, and Spec Owner approval — the same completion gate discipline Scrum and Kanban use.

## Choosing between spec-driven, Scrum, and Kanban

All three are equally supported Method Packs; `spec-driven` is only the *default*, not a requirement.

- Prefer **spec-driven** for small teams, solo developers, or an agent-paired workflow where the
  clarify-before-plan discipline matters more than sprint cadence or continuous-flow WIP limits.
- Prefer **Scrum** when the team already runs sprints and needs the Product Owner / Scrum Master /
  Developer split — see [Scrum delivery](scrum-delivery.md).
- Prefer **Kanban** for continuous flow with WIP limits and no fixed iteration — see the Kanban
  equivalent of this guide's commands, using `service-request-manager`, `flow-manager`, and `delivery`
  roles.

Switch at project creation with `agora configure --default-method scrum` (or `kanban`), or per swarm
with `agora swarm create --method scrum`.
