# Core 0.8 application hardening

Core 0.8 closes the residual application-boundary gaps documented after 0.7 without changing the
Markdown-first, Git-native, local-first architecture.

## Delivered behavior

- External artifacts can carry an explicit content SHA-256; `repo://` content is calculated locally
  and remote content is never downloaded.
- Method Pack gates may require content-addressed evidence and return an explicit blocker when it is
  missing.
- Work Control v3 retries content-fingerprint changes and returns a stable concurrent-edit error
  rather than a mixed projection.
- Gate preparation has a configurable UTC TTL, an exact expiration boundary, and a deliberate
  offline opt-out.
- Adopted work lifecycle mutations stage domain records, events, and Activity through the shared
  reentrant filesystem transaction.
- Commit, verified rollback-failure, and indeterminate transaction outcomes are distinct and
  serializable. Classification follows a post-rollback comparison of existence, content, and mode,
  rather than the presence of a rollback exception alone.
- Gate preparations return one content-digest entry for each selected evidence reference and no
  unselected entries. Confirmation requires exact equality, including explicit `null` values.
- Actor-key changes, handoffs, lifecycle preparation/apply, Session state transitions, and Tool Run
  state transitions now keep their domain record, events, and Activity writes aligned.
- Tool and Session external processes run outside filesystem transactions. Tool execution also
  releases the project writer lock before invoking the external process.
- Criterion, artifact, and evidence lifecycle actions use the first declarative mutation-handler
  registry while Workspace remains compatible.
- Application error v2 publishes provider-neutral categories, retryability, recovery hints, safe
  details, and secret redaction.
- Parent-authorized budget amendments use signed prepare/apply contracts, append-only history, usage
  floors, sibling capacity checks, and exact Activity.
- Jira live verification is create-only, disabled by default, requires an authenticated native ACLI
  plus explicit non-production confirmation, and reports manual cleanup.

## Durable schemas

New work uses `agora/artifacts/v2` and `agora/evidence/v2`; Core continues reading their v1 forms and
migrates a register when it next writes it. Budget history uses `agora/budget-amendment/v1`.
Application contracts changed only under new schema identifiers; 0.5, 0.6, and 0.7 fixtures remain
unchanged as historical compatibility evidence.

## Limits retained

The transaction is not crash-safe across process or machine loss. It snapshots the complete staged
write-set, checks each destination before replacement, and verifies staged content after commit, but
an external writer can still modify a file after the final verification. Specialized pack,
registry, trust, and upgrade staging remains separate. The Jira live baseline intentionally does
not delete, comment, or transition remote items. None of these limits changes Markdown and Git as
the source of truth or grants Studio a direct persistence path.
